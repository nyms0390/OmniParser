# Procedure Template Format

This note records the target template format for a later refactor of TASK
mode procedure execution.

## Motivation

The current template model separates top-level `inputs` from procedure
`outputs`, but the runner behaves like a data pipeline:

- user-provided values seed the first row;
- each execution reads values from the current row;
- each execution writes generated values back into the row;
- list-like fields can expand one row into many rows;
- the final CSV is an export view over the accumulated rows.

The template should expose that model directly. Users should think in terms of
fields, executions, row expansion, and export columns, not a strict
input/output split.

## User-Written Template

Users may write field names in Traditional Chinese. Each field also carries an
English `key` generated by another LLM automation tool. The Chinese name is the
display label; the English key is the stable internal identifier.

```yaml
name: 發票資訊擷取
description: 從使用者上傳的發票檔案中擷取關鍵資訊，並匯出結果表。

fields:
  發票檔案:
    source: user
    kind: file
    multiple: true
    expand: true
    key: invoice_file

  發票號碼:
    source: generated
    kind: scalar
    key: invoice_number

  供應商名稱:
    source: generated
    kind: scalar
    key: supplier_name

  發票日期:
    source: generated
    kind: scalar
    key: invoice_date

  明細項目:
    source: generated
    kind: row
    expand: true
    key: line_item

  證據截圖:
    source: generated
    kind: file
    key: evidence_screenshot

export:
  - 發票檔案
  - 發票號碼
  - 供應商名稱
  - 發票日期
  - 明細項目
  - 證據截圖

executions:
  - id: extract_invoice_header
    title: 擷取發票抬頭資訊
    foreach: 發票檔案
    uses:
      - 發票檔案
    writes:
      - 發票號碼
      - 供應商名稱
      - 發票日期
      - 證據截圖
    steps: |
      1. 開啟 <發票檔案>。
      2. 找到發票號碼、供應商名稱和發票日期。
      3. 儲存發票號碼、供應商名稱、發票日期。
      4. 擷取目前畫面作為證據截圖並儲存。

  - id: extract_invoice_lines
    title: 擷取發票明細
    foreach: 發票檔案
    uses:
      - 發票檔案
      - 發票號碼
    writes:
      - 明細項目
    steps: |
      1. 開啟 <發票檔案>。
      2. 找到發票明細表。
      3. 逐列讀取明細項目。
      4. 儲存所有明細項目。
```

## Corrected Internal Template

The parser should normalize the user-written template into an internal template
where all references use English keys. Chinese labels are preserved for UI,
agent prompt clarity, and final export headers.

```yaml
name: 發票資訊擷取
description: 從使用者上傳的發票檔案中擷取關鍵資訊，並匯出結果表。

fields:
  invoice_file:
    label: 發票檔案
    source: user
    kind: file
    multiple: true
    expand: true

  invoice_number:
    label: 發票號碼
    source: generated
    kind: scalar

  supplier_name:
    label: 供應商名稱
    source: generated
    kind: scalar

  invoice_date:
    label: 發票日期
    source: generated
    kind: scalar

  line_item:
    label: 明細項目
    source: generated
    kind: row
    expand: true

  evidence_screenshot:
    label: 證據截圖
    source: generated
    kind: file

export:
  - invoice_file
  - invoice_number
  - supplier_name
  - invoice_date
  - line_item
  - evidence_screenshot

executions:
  - id: 1
    title: 擷取發票抬頭資訊
    foreach: invoice_file
    uses:
      - invoice_file
    writes:
      - invoice_number
      - supplier_name
      - invoice_date
      - evidence_screenshot
    steps: |
      1. 開啟 <invoice_file>（發票檔案）。
      2. 找到發票號碼、供應商名稱和發票日期。
      3. 儲存 invoice_number（發票號碼）、supplier_name（供應商名稱）、invoice_date（發票日期）。
      4. 擷取目前畫面作為 evidence_screenshot（證據截圖）並儲存。

  - id: 2
    title: 擷取發票明細
    foreach: invoice_file
    uses:
      - invoice_file
      - invoice_number
    writes:
      - line_item
    steps: |
      1. 開啟 <invoice_file>（發票檔案）。
      2. 找到發票明細表。
      3. 逐列讀取 line_item（明細項目）。
      4. 儲存所有 line_item（明細項目）。
```

## Field Model

The field schema should stay small:

```yaml
fields:
  <label>:
    key: <english_internal_key>
    source: user | generated
    kind: scalar | row | file
    multiple: true | false
    expand: true | false
```

Field rules:

- `key` is required in the user-written format and must be ASCII, unique, and
  stable.
- `label` is derived from the user-written field name and may contain Chinese
  or any other UTF-8 text.
- `source: user` means the value is supplied before the run, such as typed
  values or uploaded files.
- `source: generated` means an execution must write the value during the run.
- `kind: scalar` is a single text value.
- `kind: row` is table-like data read from a screen or document.
- `kind: file` is a file reference, not plain text.
- `multiple: true` means the field value can contain a list.
- `expand: true` means each produced value creates one dataframe row.

`multiple` and `expand` are intentionally separate. A multi-file field can be
passed to one execution as a list by setting `multiple: true` and
`expand: false`, or it can create one work row per file by setting both to
`true`.

## Files

Files should be first-class field values:

- uploaded files seed `source: user`, `kind: file` fields;
- generated files are written to `source: generated`, `kind: file` fields;
- a file value should be stored internally as a structured file reference with
  at least path, display name, and MIME type when available;
- final CSV export may render file fields as paths or display names;
- JSON/debug artifacts should preserve the structured file metadata.

Example file field:

```yaml
fields:
  發票檔案:
    key: invoice_file
    source: user
    kind: file
    multiple: true
    expand: true
```

## Implementation Changes

### Parser

Update `omnitool/gradio/config/task_template.py`:

- Replace top-level `inputs` plus procedure-level `outputs` parsing with
  `fields`, `executions`, and `export`.
- Add a `TaskField` dataclass with `key`, `label`, `source`, `kind`, `multiple`,
  and `expand`.
- Add a `FieldSource` enum with `user` and `generated`.
- Add `file` to the field kind enum, or replace the current `ColumnKind` with a
  new `FieldKind` enum containing `scalar`, `row`, and `file`.
- Validate that every field key is unique and ASCII.
- Validate that every label is unique after Unicode NFC normalization.
- Validate that every `foreach`, `uses`, `writes`, and `export` reference
  exists as either a label in the user-written template or a key in the
  corrected internal template.
- Normalize all references to internal keys during load.
- Preserve `label_by_key` for UI display, prompt construction, and export
  headers.

### Procedure Runner

Update `omnitool/gradio/core/procedure_runner.py`:

- Seed the dataframe from `source: user` fields instead of the old
  `template.inputs` list.
- Add uploaded file values to the initial dataframe before procedure execution.
- Use `export` to choose CSV columns instead of all procedure outputs.
- Use `foreach` to decide which rows an execution should run against.
- Keep `expand: true` as the row-expansion behavior currently implemented by
  `explode_row`.
- Merge only fields declared in `writes`.
- Treat `kind: file` writes as file references and validate that generated file
  paths live under the session run folder or upload folder.
- Write CSV with UTF-8 BOM (`utf-8-sig`) if the output is intended for Excel.
- Keep structured JSON output alongside CSV so file fields do not lose
  metadata.

### Agent And Tools

Update `omnitool/gradio/core/agents/base.py`,
`omnitool/gradio/core/agents/react_agent.py`, and
`omnitool/gradio/core/tools/schemas.py`:

- Rename the agent-facing concept from `outputs` to writable fields in prompts.
- Validate `read_field` and `save_field` against `execution.writes`.
- Add or adapt a tool path for saving generated file fields, for example a
  `save_file` tool or a `save_field` variant for `kind: file`.
- Keep scalar and row fields on the existing read/save staged-read flow.
- Ensure `finish()` emits facts using internal keys only.

### UI

Update `omnitool/gradio/ui/app.py` and `omnitool/gradio/ui/callbacks.py`:

- Show Chinese labels in dropdowns, summaries, and exported table previews.
- Keep internal keys out of the primary UI unless debugging.
- Bind uploaded files to `source: user`, `kind: file` fields before the runner
  starts.
- Render file outputs as links or file chips in the procedure summary.
- Keep the single-execution preview path, but show the resolved row inputs and
  writable fields using labels.

### Compatibility

The migration can be staged:

1. Add a new parser path for the `fields` format.
2. Convert the new format into the current internal `TaskTemplate`,
   `TaskProcedure`, and `TaskExecution` objects where possible.
3. Refactor runtime dataclasses once behavior is covered by tests.
4. Keep old templates readable for one transition period, or provide a script
   that converts old `inputs`/`outputs` templates into `fields` templates.

### Tests

Add tests for:

- Chinese labels with ASCII keys;
- reference normalization from labels to keys;
- duplicate labels after Unicode normalization;
- duplicate keys;
- `foreach` over generated fields;
- uploaded files expanding one row per file;
- multi-file fields with `expand: false`;
- generated file outputs;
- CSV export using labels as headers;
- JSON export preserving file metadata;
- agent prompt construction showing both key and label;
- tool calls rejecting labels and accepting internal keys.
